# 吃点什么 · 自用 PWA v0

手机优先的静态网页应用。纯 HTML/CSS/JavaScript，无构建依赖、自建服务器、账号或私密 API 密钥、广告或分析追踪。适合放在 GitHub Pages 项目子路径。

## 已实现

- 四步首次建档：忌口/过敏、异常体检项/已知疾病、6道口味二选一、确认保存。可回退、跳过偏好及后续编辑。
- 三页主导航：今天、吃过、我的。
- 42份自制餐食模板；添加、编辑、删除个人餐食，登记实际配料和过敏原。
- 根据已登记的配料约束、就餐方式、口味和减脂／健身意向进行本地候选筛选。
- “我很想吃”在本地与已自动获取的中文食谱中匹配，每次展示一套。
- 一键换一套、区分计划和实际吃过、反馈及备注、历史餐食重新检查。
- localStorage本机保存；完整备份/仅餐食库备份、校验后导入恢复、清空。
- Web App Manifest、普通及maskable PNG图标、Service Worker离线壳、手动更新提示、安装引导。
- GitHub Actions部署工作流，仅发布明确列出的静态程序文件。

## 当前边界

**这是可运行的自用餐食选择工具，不是已验证的疾病个性化推荐系统。**

桥本和银屑病相关情况可记录、编辑并查看覆盖状态；疾病食物规则、药食相互作用和报告解读尚未经过专业审核，因此不会用于治疗性排序或食物安全保证。覆盖范围在推荐卡片后的折叠说明中展示。主目标不用于自动计算能量目标。

过敏检查依赖录入信息完整准确。内置模板没有核实实际厨房交叉接触，故有已知过敏时需要先编辑核实对应餐食，才能进入候选。未知过敏原或配料不全时不自动放行。无过敏原标记不等于无风险。

外卖/食堂/便利店没有定位或实时供应数据；模板可作为点餐灵感，实际配料和供应需核对。已移除预算和时间筛选及展示；旧备份中的字段只为兼容保留，不参与推荐。

## 本地启动

需要 Python 3。终端进入本目录运行：

```sh
python3 -m http.server 4173 --bind 127.0.0.1
```

然后打开 <http://localhost:4173/>。不要直接双击index.html：ES modules和Service Worker需要HTTP(S)，离线功能仅在HTTPS或localhost安全上下文启用。

手机不应通过普通局域网HTTP地址验证PWA安装能力；正式手机体验使用部署后的GitHub Pages HTTPS地址。

## GitHub Pages部署

1. 新建仓库，把**本目录里的内容**放到仓库根目录，包含`.github/workflows/pages.yml`，不要只上传外层文件夹。
2. 默认分支使用`main`。若用其他分支，修改工作流的触发分支。
3. 在仓库`Settings → Pages → Build and deployment → Source`选择`GitHub Actions`。
4. 推送到`main`，或在Actions中手动运行`Deploy PWA to GitHub Pages`。
5. 等工作流完成后使用Pages给出的HTTPS地址。支持`https://用户名.github.io/仓库名/`，无需修改代码中的路径。
6. 首次联网打开，等待离线资源安装完成，再尝试添加到主屏幕；iOS通常从Safari分享菜单添加，Android从浏览器菜单安装。

也可在Pages选择从`main`根目录发布，但会连同README等仓库内容一起公开，推荐使用本项目工作流的静态文件白名单。

**只上传程序。** 体检报告、私人备份、健康截图、个人档案都不要放到仓库中。`.gitignore`排除常用`*.backup.json`备份文件名，但不能识别所有个人文件，上传前仍应核对。

本次修改保存在本地，尚未推送；现有线上版本需等下一次 Pages 部署完成后更新。

## 隐私与存储

- 表单和记录保存在当前浏览器的localStorage，未加额外密码加密；不要把本地保存理解为访问控制。
- 同一设备不同浏览器、或更换网站域名/存储位置不会自动同步；卸载、清缓存或隐私模式可能丢失记录。
- Pages托管方会收到普通静态资源请求及网络元数据；健康表单不上传；自动获取中文食谱的请求不包含档案、口味答案或用户输入的想吃内容。
- 同一域名下其他页面属于相同浏览器来源，避免同源托管不受信任脚本。公开源码并不公开localStorage数据，但同源脚本有访问能力。
- 完整导出含敏感资料。仅餐食库导出不含档案、计划、历史；自填的餐食备注仍可能含私人内容，分享前自行检查。
- 导入会替换当前数据、要求重新检查计划。先导出旧数据再恢复。
- 清空应用数据不删除已下载到设备上的备份文件。

## 更新与离线

Service Worker只缓存静态程序资源，不缓存健康表单请求（本应用没有此类请求）。首次成功安装后可离线访问。

修改静态程序文件后，同时更新 `updates.js` 的 `APP_VERSION`、`sw.js` 的缓存版本与 `GET_VERSION` 返回值。打开的旧版本会在新worker安装完成后显示更新提示。安装阶段不会强制打断当前页面；点击更新才切换。更新前会尽量保存建档草稿。

## 检查

需要Node.js 22或更新版本，无需npm install：

```sh
npm test
```

测试覆盖：过敏别名与未知过敏原、未确认交叉接触、硬限制与偏好区别、无候选不放宽限制、健康覆盖提示、档案变化使计划失效、实际记录、备份脱敏及非法导入。

交付环境中，启动localhost预览服务受沙盒限制；自动审批因503失败而未执行。因此自动逻辑测试已执行，但浏览器视觉、真实Service Worker离线和手机安装测试尚未完成，不能宣称已通过。

上线前手动检查：

- 用真实手机在320—430px布局完成建档，测试键盘、返回与修改。
- 增加过敏项后，旧计划必须重新检查；未知配料不能被放行。
- 完整导出、清空、导入，检查恢复正确且没有上传健康档案的网络请求。
- 在线打开后关闭网络并重新打开；确认离线壳和数据可用。
- 安装到主屏幕，再发布一次新版本，验证更新提示。
- 从项目子路径打开，确认manifest、图标、模块和worker均无404。

## 文件

`app.js`：界面与本机状态。`core.js`：验证、筛选、计划和备份。`data.js`：问题、模板与过敏原别名。`sw.js`：离线缓存。`tests/`：无依赖逻辑测试。


## v0.3 当前体验

- 首次打开直接进入建档，可暂存后稍后继续；老用户保留原档案、计划和记录。
- 减脂、健身或两者兼有可在建档末页选择，之后到“我的 → 饮食与健康档案”修改。排序只使用口味与配料特征，不推算热量或疾病适宜性。
- 推荐卡片优先显示，“本次考虑了什么”收起放在其后；不再要求逐次通过健康提示。常规浏览只展示推荐理由，过敏和明确忌口仍是硬约束。
- 离线模板 42 份，老版本升级只补充新模板一次，不覆盖编辑过的旧模板。
- 更新提示核对等待中的 worker 版本；初次安装、没有等待版本、同版本都不显示。

## 自动中文食谱与隐私

默认使用 [HowToCook 中文食谱库](https://github.com/Anduin2017/HowToCook)，遵循其 [Unlicense](https://github.com/Anduin2017/HowToCook/blob/master/LICENSE)。原文可从每张联网推荐卡中的“中文做法”链接查看。它是烹饪资料，不是临床饮食规则库。

建档完成后或老用户打开时，自动请求 GitHub 目录，再从荤菜、素菜、水产、主食、早餐、汤等目录每天轮换选取最多 24 份，按同一个目录提交版本读取配料。并发最多 4 个、总超时 18 秒。来源不可用时继续使用已有餐食；成功结果本机缓存 24 小时。无独立搜索页面，无需用户输入搜索词或先手动导入。

程序优先展示通过本地约束检查的中文联网餐食，在该候选池中按口味与目标排序。普通独立菜品会视已有配料补充米饭、小白菜或豆腐等搭配，组合后的完整候选再次检查。每次只展示一套，点“换一套”直接跳过当前套；不会同时展示多个备选，也不会先询问换餐原因。已选计划不会同时展示另一套推荐。

中文来源仍不代表配料完整或过敏核对完成。网上食谱始终标为实物配料和交叉接触未确认：有明确忌口或已知过敏时，无法核对的网上候选不会自动进入推荐，而使用满足现有检查的本地候选；无候选时提示核对常吃清单。不会为了联网推荐放宽硬限制，也不提供疾病适宜性或治疗建议。

网络请求只用于获取公开目录和菜谱文件，不发送健康档案、口味答案、目标、定位、历史或想吃内容。所有筛选在本机执行；GitHub 服务仍可接收普通访问元数据。网页不渲染来源中的 HTML、外部图片或营养/医学描述。断网继续使用缓存与离线模板。

`online.js` 负责中文目录与配料解析；`recommendations.js` 负责缓存校验、整餐搭配和统一推荐；部署白名单与 Service Worker 已包含它们。v0.3 修改保存在本地，需推送后部署。无需清空个人档案。

验证：自动测试覆盖中文源解析、后台自动获取、单套展示与换餐、超时/失败回退所需的错误处理、来源地址限制、配料硬约束、选定套餐保存与历史。真实手机、浏览器跨域获取和更新安装流程仍需部署后验证；本环境此前启动预览服务器时自动审批服务返回 503。
